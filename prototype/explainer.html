How a no-build page loads iterate's stream viewer from esm.iterate.com

An agent writes one HTML file. It imports ContextView, the stream viewer, from esm.iterate.com, and the browser runs it. Nothing is built while the page loads. Everything was built earlier, once, when packages/ui changed on main.

  • "ui"packages/ui in iterate/private, published as @iterate-com/ui: iterate's React component kit. ContextView lives in it, beside the repo IDE and shadcn's components.
  • When it bundlesIn CI, after a change to packages/ui merges. tsdown builds ui and copies the libraries it uses (React, Base UI, CodeMirror, the SDK's browser client) into ui's own output files, in chunks that ui's entry points share. The output is committed to iterate/packages.
  • At load timeThe browser asks esm.iterate.com for files. The service finds them in iterate/packages at a commit and serves them. Every chunk has one URL, so the page runs one React and one CodeMirror, and nothing comes from esm.sh.
Terms used on this page
packages/ui
The folder in iterate/private holding iterate's React components (.tsx source with Tailwind classes). Its package name is @iterate-com/ui.
iterate/packages
The public GitHub copy of iterate/private's packages/ and configs/, made by Copybara after every change on main. In this design it also holds packed/<package>/: each package's built files.
build, bundle
Turning a package's source into files a browser can run. Bundling copies the code of the libraries it imports into those files, instead of leaving import "react" for someone else to satisfy.
entry, chunk
An entry is a file a page imports by name (./page, ./components/context-view/context-view). A chunk is a file entries share, such as vendor-react.mjs, so code that two entries need is downloaded and run once.
esm.iterate.com
The proposed service (a Cloudflare Worker). It serves files from packed/ at a commit, as ES modules to browsers and the platform's loader, and as npm tarballs to package managers. The prototype runs on localhost:8797.
esm.sh
A public service that turns npm packages into browser modules on request. Our worker packages' npm dependencies still come from it. Our browser package no longer does (section 4).
ref, commit
ref=main names whatever main is now. esm.iterate.com answers it with a redirect to the commit (a 40-character sha), so every file's URL names one build forever and can be cached forever.
one URL, one module
A browser runs each module URL once. Two URLs with the same code are two separate copies: two Reacts that don't know about each other.
1 · The page

What the agent writes

Two shapes of the same page. Each is a whole file: save it anywhere and open it while the prototype runs on localhost:8797. In production the URLs would start https://esm.iterate.com/ and name repository=iterate/packages.

Full URLs, no import map One stylesheet, two imports, nothing to set up

Every import is a full esm.iterate.com URL. ui's page entry gives the page React's API and html, a JSX-like tag that needs no compiler, from the same React the components use. 


      

    

    

      
        An import map, bare imports
        Imports read like normal code; other React libraries can join
      
      

        An inline <script type="importmap"> says where each name comes from, so the
        page imports react and @iterate-com/ui/… by name. react,
        react-dom/client and react/jsx-runtime point at ui's own React. A
        React library from esm.sh, loaded with ?external=react (react-query here), imports
        that same React: its useQuery runs beside ContextView with one React on the page.
      

      

        One line per entry. With query-parameter URLs, a single "@iterate-com/ui/" line
        can't cover the whole package: the browser resolves the rest of the name as a relative URL,
        which drops the query, and refuses it ("blocked due to backtracking"). A path-shaped URL
        would let one line map all of ui.

3 · Where the files come from

    
The bundling happens in CI, once per change

    
    
      
  1. 
        
    
          In iterate/private
          
    
            Someone changes packages/ui and it merges to main. The source is .tsx that
            imports react, @base-ui/react, @codemirror/view and
            its own files as #/components/ui/button.tsx. A browser can run none of it as
            written.
          
    
        
    
      
    2. 
      
  2. 
        
    
          In CI, the copy-packages workflow
          
    
            Copybara copies the source to iterate/packages. Then tsdown builds packages/ui. That's the
            bundling: the code of every library ui imports goes into ui's output files, grouped into
            chunks named by library (vendor-react.mjs, vendor-base-ui.mjs,
            vendor-codemirror.mjs). Tailwind compiles styles.css. One more
            commit puts the result in packed/@iterate-com/ui/. About 0.3 s of build.
          
    
        
    
      
    3. 
      
  3. 
        
    
          At load, esm.iterate.com
          
    
            The page asks for @iterate-com/ui at ref=main,
            path=./page. The service looks up main's commit and redirects there. It reads
            packed/@iterate-com/ui/package.json at that commit to find which file
            ./page means, and serves the file from GitHub. It rewrites the file's imports to
            full esm.iterate.com URLs at the same commit: a browser can't resolve
            ./vendor-react.mjs against a URL whose file is named in a query parameter.
          
    
        
    
      
    4. 
      
  4. 
        
    
          At load, the browser
          
    
            It follows the imports. Each chunk has one URL, so each runs once. CodeMirror is only
            imported with import(), so it downloads when the viewer first shows code.
          
    
        
    
      
    5. 
    

    

      Worker packages (voice, docs, github-sync) are built the same way but not bundled. Their files
      keep imports like pako, which the service points at esm.sh, and the platform's loader
      fetches and locks per project. A worker has no React to keep single.
    

  


  

    
4 · Why ui bundles its libraries

    
With esm.sh supplying React, the page got two

    

      The first prototype left ui's imports alone and pointed them at esm.sh, at the exact versions in
      iterate's lockfile. esm.sh builds each package with its own settings written into the URL, and
      works those settings out per package. The page's React and react-dom's React came out as two
      URLs, so two copies ran.
    

    

      
the page's React        https://esm.sh/react@19.3.0/es2022/react.mjs
react-dom's own React   https://esm.sh/react@19.3.0/X-ZEBiYXNlLXVp…/es2022/react.mjs

5 · Size

    
Where the bytes are

    

      ui's whole build, unminified, by library. CodeMirror is two-fifths of it and only downloads when
      a code view opens.
    

    

    

    

      React (and CodeMirror) could become peers, loaded from somewhere other than ui's build. That
      only works if every importer reaches React by the same URL, which is what section 4 failed to
      get from esm.sh. Bundled, the cost is repo bytes once per library version, not once per ui
      build, because the vendor chunks don't change when ui's own code does.
    

  


  

    
6 · Live data

    
A real context instead of sample events

    

      The demo feeds ContextView sample events. A live page signs its visitor in and reads a context.
      The pieces exist: a project's hosts already serve the platform's sign-in (/.auth/*)
      and API (/api), as Notes uses them, and the SDK's
      createIterateClient() is written for a plain page. ui's build bundles that client
      as a live entry, so its hooks share ui's React.
    

    

    

      Built, not yet run: the live entry is in this build (130 KB), but no page has used it
